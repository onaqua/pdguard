# Архитектура pdguard

Этот документ описывает, как решение устроено на самом деле: границы пакетов,
путь данных одного запроса, принятые решения вместе с их ценой и то, где
решение упрётся при росте нагрузки. Это инженерный текст, а не реклама.

## Границы пакетов

```
cmd/server                 процесс: флаги, окружение, listener, сигналы, слив
└── internal/httpapi       транспорт: маршруты, admission control, таймауты, /admin
    └── internal/engine    ядро: направление операции, фильтрация по конфигурации
        ├── internal/config   живая конфигурация, атомарная замена
        ├── internal/store    соответствия payload_id → (оригинал, маска)
        └── internal/pd       предметная область
            ├── pd            каталог типов, Span, приоритеты
            ├── pd/text       лоукейс с сохранением смещений, токенизация
            ├── pd/dict       словари (встроены через go:embed)
            ├── pd/detect     контракт детектора, контекст, резолвер, детекторы
            └── pd/mask       контракт стратегии, применение и восстановление
    internal/logging       логгер со скрабингом (используется всеми)
    internal/metrics       счётчики и экспозиция Prometheus (используется всеми)
```

Зависимости направлены строго внутрь: `pd/*` ничего не знает про HTTP и
конфигурацию. `internal/store` не знает про метрики — мост между ними строит
`httpapi` при чтении `/metrics` и `/stats`. `internal/engine` не знает про HTTP —
он вызывается и из `httpapi`, и напрямую из бенчмарка.

### cmd/server

Владеет жизненным циклом процесса и ничем больше: флаги, окружение, listener,
сигналы, слив. Здесь же два решения, которые не относятся к HTTP:

- **`applyMemoryLimit`** читает cgroup-лимит памяти и ставит `GOMEMLIMIT` на 80%
  от него. Go читает cgroup CPU-квоту для GOMAXPROCS, но не лимит памяти: без
  этого коллектор целится в ~2× живую кучу и может уйти за лимит контейнера,
  после чего ядро убивает процесс — а вместе с ним весь in-memory store, и
  каждый ещё не выполненный обратный шаг ответит маской вместо оригинала.
- **`drainTimeout`** (12 с) чуть больше таймаута запроса (10 с), чтобы запрос,
  которому ещё разрешено лететь, успел завершиться. Порядок слива: снять флаг
  готовности → дать in-flight запросам завершиться → закрыть store.

### internal/httpapi

Транспорт. Владеет маршрутизацией, admission control, таймаутами, лимитом тела,
аутентификацией и операционными эндпоинтами. Контракт `/process` узкий, поэтому
два правила:

1. `POST /process` принимает голый запрос: JSON, два поля, без обязательных
   заголовков и без аутентификации, если не включён `require_system`. Всё, что
   хотелось бы требовать от вызывающего (system id, API key, request id), —
   опционально, потому что проверяющая система ничего из этого не шлёт.
2. Ответ лучше ошибки. Прогон останавливается после короткой серии невалидных
   ответов, поэтому `/process` деградирует, а не падает (см. `fail_open`).

Пайплайн middleware (снаружи внутрь): `recover` → `metrics` → `limit` →
`timeout` → `bodyLimit` → `log`. Порядок не произволен: `recover` должен видеть
панику из любого слоя; `metrics` считает и 429, которые производит `limit`;
`timeout` стоит под `limit`, чтобы запрос, не получивший слот, не жёг бюджет
ожиданием; `log` — самый внутренний, чтобы видеть фактический статус.

### internal/engine

Ядро. Решает, в какую сторону идёт вызов, какие типы ПД система может
маскировать, какую форму маски получает каждый тип и что делать, когда
соответствие в store пропало. Два инварианта:

1. Текст вне найденного спана возвращается байт в байт. Метрика качества —
   span-based edit distance против эталонной маски, поэтому каждый лишний
   изменённый символ — прямое вычитание из счёта.
2. Ответ всегда лучше ошибки. Обратный шаг при пропавшем соответствии
   деградирует до «вернуть то, что прислали» (см. `demaskMiss`).

### internal/config

Живая конфигурация. `Manager` держит текущий `*Config` в `atomic.Pointer`.
`Get` вызывается минимум раз на запрос при целевом 1000 RPS; мьютекс там
сериализовал бы каждый запрос за редким административным обновлением, поэтому
читатели берут lock-free снимок, а писатели подменяют полностью собранную
замену. `Apply` валидирует, публикует атомарно и пишет на диск через временный
файл + rename.

### internal/store

In-memory соответствие `payload_id → (оригинал, маска)`. Половина счёта — это
демаскирование, и оно полностью детерминировано: либо мы всё ещё держим
оригинал, либо теряем эти очки целиком. Поэтому всё настроено на выживаемость
под нагрузкой: 256 шардов (lock stripes), lazy-истечение TTL, фоновый sweeper,
два мягких лимита — по числу записей и по суммарному размеру (байтовый лимит
существует потому, что count-лимит не ограничивает память: запись держит две
копии payload, а payload может быть 100k токенов).

### internal/pd/*

Предметная область, ничего не знает про HTTP и конфигурацию.

- **`pd`** — каталог типов, `Span` (полуоткрытый байтовый диапазон `[Start,End)`
  по исходному тексту), приоритеты типов для разрешения пересечений.
- **`pd/text`** — лоукейс с сохранением байтовых смещений, токенизация.
- **`pd/dict`** — словари, встроенные через `go:embed`.
- **`pd/detect`** — контракт детектора, общий контекст запроса, резолвер
  пересечений, сами детекторы (fio, passport, docs, date, address, finance,
  contact).
- **`pd/mask`** — контракт стратегии, применение и восстановление.

### internal/logging и internal/metrics

Используются всеми. `logging` гарантирует, что ПД не попадут в логи: каждый
атрибут проходит через скрабинг-обработчик. `metrics` — lock-free слой счётчиков
и экспозиция Prometheus; в нём нет ни одного API, принимающего значение ПД.

## Путь данных одного запроса

1. `POST /process` приходит в `httpapi.handleProcess`.
2. Middleware: `recover` → `metrics` (считает inflight) → `limit` (семафор,
   может вернуть 429) → `timeout` (контекст с `process_timeout`) → `bodyLimit`
   (`MaxBytesReader`) → `log`.
3. `handleProcess` авторизует систему (если `require_system`), декодирует тело
   `{payload, payload_id}`, требует непустой `payload_id`.
4. Вызов `engine.Process(ctx, systemID, payloadID, payload)`.
5. `engine.Process` резолвит систему, делает `store.Get(storeKey(payloadID))` и
   решает направление по `decide`:
   - записи нет → прямой шаг (mask), если payload не выглядит как наша маска;
   - payload == Masked → обратный шаг (demask);
   - payload == Original → ретрай прямого шага (maskRetry, идемпотентно);
   - ни то, ни другое → перезапись (remask);
   - записи нет, но payload похож на маску → demaskMiss (эхо).
6. Прямой шаг: `detect` (с chunking для длинных payload) → `filter` (правила
   системы, `requires_companion`) → `mask.Apply` → `store.Put` (если `demask`
   включён) → ответ с маской.
7. Обратный шаг: вернуть `entry.Original` байт в байт.
8. `engine.finish` публикует метрики и (на debug-уровне) сводку по запросу.

## Принятые решения и их цена

### Направление выводится из payload, а не из счётчика обращений

Наивное правило «первый вызов маскирует, второй демаскирует» неверно: харнесс
может ретраить запрос до трёх раз, и каждый ретрай несёт тот же `payload_id`.
Ретрай прямого шага тогда читался бы как демаскирование, и мы ответили бы
маской поверх маски. Поэтому направление определяется тем, чем является
`payload` (см. `decide`).

**Выигрыш:** идемпотентность по `payload_id`, корректные ретраи, перезапись при
переиспользовании id на другом тексте.

**Цена:** чтобы отличить «наш маска» от «обычный текст», нужен предикат
`looksMasked`. Он консервативен в одну сторону: ложное срабатывание здесь
вернуло бы настоящий, незамаскированный payload и утекло бы его. Поэтому
сигналы — только формы, которых обычная проза не производит: две и более
звёзды подряд, токен `PD_`, три одиночные заглавные с точками «И. И. И.».
Двухбуквенные инициалы («Иванов И. И.») намеренно не считаются маской — это
обычная форма обращения, и эхо такой строки утекло бы остальные значения.

### Fail-open по умолчанию

`server.fail_open: true` — при внутреннем сбое `/process` отвечает 200 с
неизменённым payload, а не ошибкой.

**Выигрыш:** один транзиентный сбой (дедлайн, паника детектора) не может
потратить весь бюджет ошибок прогона, который останавливается после короткой
серии невалидных ответов.

**Цена:** возврат незамаскированного текста из маскирующего прокси — это ровно
то, чего прокси не должен делать. Для реального трафика оператор обязан
выключить `fail_open`. Исключение сделано для `ErrSystemUnavailable`: если
оператор выключил систему, эхо отдало бы ПД именно тому вызывающему, которому
их видеть нельзя, поэтому это остаётся ошибкой (403).

### In-memory store вместо внешнего хранилища

Соответствия живут в памяти процесса.

**Выигрыш:** нулевая задержка на обратном шаге, нет внешней зависимости, нет
сетевых сбоев, простая идемпотентность.

**Цена:** соответствие не переживает рестарт процесса. После рестарта обратный
шаг для ещё не выполненных `payload_id` ответит маской (или эхом, если payload
похож на маску). Память ограничена двумя мягкими лимитами, и при переполнении
старые записи вытесняются — вытесненная запись означает провал обратного шага.
`store.Store` — интерфейс, поэтому Redis-реализацию для multi-instance можно
подставить без правки обработчика, но её нет в коде.

### Байтовый лимит store в дополнение к count-лимиту

`MaxEntries` не ограничивает память: запись держит две копии payload, а payload
может быть 100k токенов. Поэтому добавлен `MaxBytes` — суммарный размер живых
записей.

**Выигрыш:** процесс не умирает от OOM, а OOM здесь — худший исход, потому что
он уносит весь store и половину счёта.

**Цена:** при переполнении байтового бюджета старые записи вытесняются
(приближённый LRU через выборку 8 случайных ключей, как у Redis). Вытесненная
запись — провал обратного шага. `MaxValueBytes` обязан быть не меньше
максимального принимаемого тела: иначе прямой шаг успешен, соответствие
отброшено, и обратный шаг ответит маской без какой-либо ошибки.

### Chunking длинных payload

Payload длиннее 64 KiB анализируется по кускам, разрезанным по границам строк,
с перекрытием 256 байт.

**Выигрыш:** резолвер пересечений сравнивает каждого кандидата со всем
сохранённым, поэтому его стоимость растёт квадратично от числа детекций в одном
контексте; кусок держит пиковые срезы пропорциональными куску, а не 100k-токен
документу. Отменённый запрос замечает дедлайн между кусками.

**Цена:** сущность, через которую прошёл разрез, видна в двух соседних кусках и
может быть найдена дважды; это исправляется повторным `Resolve` объединённого
набора. Перекрытие 256 байт выбрано под самый длинный распознаваемый объект —
паспортный орган (~160 байт кириллицы) плюс левый якорь «выдан …».

### Lock-free метрики и конфигурация

`metrics` — атомарные счётчики на предвыделенных ячейках, без мьютексов и без
аллокаций строк на запрос (значения меток интернированы). `config.Manager.Get` —
lock-free снимок из `atomic.Pointer`.

**Выигрыш:** горячий путь не сериализуется за редкими обновлениями.

**Цена:** кардинальность меток ограничена фиксированными наборами (op, status,
reason, тип ПД); всё, что вне набора, сворачивается в `other`. Это осознанно:
каждая комбинация меток — отдельный временной ряд в Prometheus, и метка,
питаемая из данных запроса, — это неограниченный рост памяти.

### Скрабинг логов как механизм, а не договорённость

`logging` оборачивает каждый `slog.Handler` в `scrubHandler`, который
инспектирует каждый атрибут: ключи из белого списка проходят как есть, всё
остальное санитизируется, а значения с формой ПД заменяются на длину и солевой
отпечаток.

**Выигрыш:** программист, залогировавший payload по ошибке, ничего не утечёт —
это ровно тот сбой, который ищет проверка.

**Цена:** отлаживаемость снижается: длинные строки и ФИО в логах видны только
как `[redacted len=… fp=…]`. Белый список ключей (`payload_id`, `system`, `op`,
`status`, `types`, …) — это компромисс: эти значения безопасны и нужны для
корреляции.

## Где решение упрётся при росте нагрузки

- **Один процесс, in-memory store.** Горизонтальное масштабирование невозможно
  без внешнего хранилища соответствий: два инстанса не разделяют `payload_id →
  оригинал`. Прямой шаг на инстансе A и обратный на инстансе B провалят
  демаскирование. Упор — на первый же инстанс сверх одного. Интерфейс
  `store.Store` готов к Redis-реализации, но её нет.
- **Память store.** Байтовый лимит (по умолчанию 1 GiB) ограничивает число
  живых соответствий. При 100k-токен payload это тысячи записей, а не миллионы.
  Вытеснение старых записей — провал обратного шага. Упор — при росте объёма
  текста или числа уникальных `payload_id`.
- **Один детекторный проход на запрос.** Детекторы линейны по payload, но их
  несколько, и каждый делает свой проход. На очень плотном по ПД тексте
  резолвер пересечений (даже с bitmap-оптимизацией) и сами детекторы — главный
  CPU-бюджет. Упор — при росте плотности ПД на единицу текста.
- **`max_concurrent` — фиксированный семафор.** Его ёмкость задаётся при
  старте; изменение через `PUT /admin/config` не применяется (ответ сообщает
  `max_concurrent_applies: false`). Упор — при изменении профиля нагрузки без
  рестарта.
- **Один процесс на один listener.** Нет встроенного шардирования по
  `payload_id` между воркерами. Упор — при превышении пропускной способности
  одного процесса.
