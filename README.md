# pdguard — Модуль безопасности персональных данных

HTTP-прокси между системой-потребителем и LLM. Сервис находит в тексте
персональные данные (ПД), заменяет их масками перед отправкой в модель, а по
тому же `payload_id` возвращает исходный текст обратно, когда модель отвечает.

Контракт — единственный эндпоинт `POST /process`, который обслуживает и прямой
шаг (маскирование), и обратный (демаскирование). Направление определяется по
`payload_id` и по тому, чем является `payload`.

## Что решает

ТЗ требует, чтобы LLM не получала персональные данные клиентов, но при этом
могла отвечать по существу. Решение — двухшаговый прокси:

1. **Прямой шаг.** Система-потребитель отправляет текст с ПД. Сервис находит
   ПД, заменяет их масками, запоминает соответствие `payload_id → (оригинал,
   маска)` и возвращает замаскированный текст.
2. **Обратный шаг.** Ответ модели (который может содержать те же ПД) с тем же
   `payload_id` отправляется в сервис. Сервис возвращает исходный текст байт в
   байт.

Текст вне найденных спанов не преобразуется вовсе: результат собирается как
«копия промежутка → маска → копия промежутка», поэтому демаскирование
возвращает исходную строку без потерь.

## Быстрый старт

```bash
docker compose up -d --build
```

Сервис поднимется на `http://localhost:8080`. Проверка живости — `GET /health`.

### Рабочий пример round-trip

Пример из ТЗ: «Клиент Иванов Иван Иванович, паспорт 4509 123456».

**Прямой шаг** — маскирование:

```bash
curl -sS -X POST http://localhost:8080/process \
  -H 'Content-Type: application/json; charset=utf-8' \
  -d '{"payload":"Клиент Иванов Иван Иванович, паспорт 4509 123456","payload_id":"8a77d363c7c044b49b41d7b8a448243a"}'
```

Фактический ответ:

```json
{"result":"Клиент И. И. И., паспорт 45** ****56"}
```

**Обратный шаг** — демаскирование с тем же `payload_id`:

```bash
curl -sS -X POST http://localhost:8080/process \
  -H 'Content-Type: application/json; charset=utf-8' \
  -d '{"payload":"Клиент И. И. И., паспорт 45** ****56","payload_id":"8a77d363c7c044b49b41d7b8a448243a"}'
```

Фактический ответ:

```json
{"result":"Клиент Иванов Иван Иванович, паспорт 4509 123456"}
```

Обратный шаг вернул исходную строку байт в байт.

## Для жюри: проверка за 5 минут

Всё уже развёрнуто и доступно снаружи — ничего локально поднимать не нужно.

**1. Демо-консоль** — https://pereshein.ru. Блок «Чат с ИИ через pdguard»: выберите
пример («Письмо клиенту», «Перевод», «Ловушка») и нажмите «Отправить в ИИ» — три
карточки покажут, что ушло в модель (ПД заменены токенами), что модель ответила и
что получил пользователь после восстановления; система analytics получает ответ без
восстановления. Блок «Маскирование и демаскирование (как в ТЗ)»: «Замаскировать»
вызывает POST /process и показывает найденные фрагменты, «Демаскировать» — обратный
шаг с тем же payload_id и сверку с исходным текстом байт в байт.

**2. Маскирование и демаскирование** — два `curl` к `POST /process` с одним
`payload_id` (пример из ТЗ):

```bash
curl -sS -X POST https://pereshein.ru/process \
  -H 'Content-Type: application/json; charset=utf-8' \
  -d '{"payload":"Клиент Иванов Иван Иванович, паспорт 4509 123456","payload_id":"8a77d363c7c044b49b41d7b8a448243a"}'
# → {"result":"Клиент И. И. И., паспорт 45** ****56"}

curl -sS -X POST https://pereshein.ru/process \
  -H 'Content-Type: application/json; charset=utf-8' \
  -d '{"payload":"Клиент И. И. И., паспорт 45** ****56","payload_id":"8a77d363c7c044b49b41d7b8a448243a"}'
# → {"result":"Клиент Иванов Иван Иванович, паспорт 4509 123456"}
```

**3. LLM-цепочка** — `curl` к `POST /v1/chat/completions` с заголовком
`X-PDGuard-Debug: 1`:

```bash
curl -sS -X POST https://pereshein.ru/v1/chat/completions \
  -H 'Content-Type: application/json' -H 'X-PDGuard-Debug: 1' \
  -d '{"messages":[{"role":"user","content":"Клиент Иванов Иван Иванович, паспорт 4509 123456"}]}'
```

В ответе поле `pdguard` показывает, что ушло в LLM (замаскировано), ответ LLM и
результат после восстановления. Защиты цепочки: ПД маскируются до отправки в
модель (токены `PD_*`); при недоступности LLM — fail-closed **503**; после ответа
модели выполняется повторная проверка на утечку — при остатке ПД ответ
отклоняется (**422**); восстановление оригинала доступно только системам с
`demask: true`; предел частоты вызовов LLM (`llm.requests_per_minute`, по умолчанию
60/мин, сверх — **429** с `Retry-After`).

**4. Логи и метрики.** По каждому запросу пишется запись `request` с типами ПД и
их количеством (сами значения не логируются). Смотреть: `docker compose logs
pdguard`. Метрики Prometheus — `GET /metrics`; дашборд Grafana поднимается
`docker compose --profile obs up -d`.

**5. Новый тип ПД без правки кода.** Опишите его в блоке `custom_types`
конфигурации (см. раздел «Конфигурация») и примените через `PUT /admin/config`
на лету — перезапуск не нужен.

## Как устроено решение

Путь одного запроса:

```
POST /process
   │
   ▼
internal/httpapi   транспорт: маршруты, admission control, таймауты,
   │               лимит тела, аутентификация, /admin, /metrics
   ▼
internal/engine    ядро: направление операции (mask/demask), фильтрация
   │               по конфигурации системы, chunking длинных payload
   ├── internal/config   живая конфигурация, атомарная замена
   ├── internal/store    соответствие payload_id → (оригинал, маска)
   └── internal/pd       предметная область
       ├── pd            каталог типов, Span, приоритеты
       ├── pd/text       лоукейс с сохранением смещений, токенизация
       ├── pd/dict       словари (встроены через go:embed)
       ├── pd/detect     контракт детектора, контекст, резолвер, детекторы
       └── pd/mask       контракт стратегии, применение и восстановление
```

Зависимости направлены строго внутрь: `pd/*` ничего не знает про HTTP и
конфигурацию. Подробно — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Конфигурация

Конфигурация — файл `configs/config.json` (JSON, только стандартная библиотека).
Ключевые блоки:

- **`systems`** — список систем-потребителей. Для каждой: `id`, `name`,
  `enabled`, `api_key`, `demask` (разрешено ли демаскирование) и `types` —
  правила по типам ПД (включён ли тип, стратегия маскирования, порог
  уверенности, правило `requires_companion`).
- **`server`** — адрес, таймауты, лимит тела, лимит конкурентности, `fail_open`.
- **`store`** — параметры in-memory хранилища соответствий `payload_id`.
- **`log`** — уровень и формат логов.
- **`default_system`** и **`require_system`** — какая система обслуживает
  запросы без заголовка `X-System-Id` и нужно ли требовать явное указание.

Краткая инструкция по настройке: отредактируйте `configs/config.json` и
перезапустите контейнер, либо примените конфигурацию на лету через
`PUT /admin/config`. Для каждой системы укажите `enabled`, `demask` и правила
по типам ПД. `require_system: true` включает allow-list по `X-System-Id` и
`X-API-Key`. Подробно — в [docs/CONFIG.md](docs/CONFIG.md).

Новый тип ПД добавляется без правки кода: опишите его в блоке `custom_types`
(имя, регулярное выражение `pattern`, необязательное слово-якорь `anchors` и
окно `window`, стратегию маскирования `strategy` и метку `label`), а
справочники публичных персон и отделений банка расширяются через блок
`dictionaries` (`famous_people`, `bank_places`). Например,
`{"custom_types":[{"name":"CONTRACT_NUMBER","pattern":"\\d{2}-\\d{6}","anchors":["договор"],"strategy":"stars_keep2"}]}`
маскирует номер договора рядом со словом «договор». Изменения применяются на
лету через `PUT /admin/config` без перезапуска.

## Наблюдаемость

- **Метрики Prometheus** — `GET /metrics`. Гистограммы латентности по операциям
  (`pdguard_request_duration_seconds`), счётчики запросов по операции и статусу
  (`pdguard_requests_total`), **RPS** (`pdguard_rps`), **TPS** (`pdguard_tps`),
  счётчики найденных категорий ПД (`pdguard_pd_detected_total`), состояние
  хранилища (`pdguard_store_*`), счётчик fallback-демаскирования
  (`pdguard_demask_fallback_total`).
- **Сводка** — `GET /stats` в JSON: версия, аптайм, квантили латентности,
  RPS/TPS, счётчики категорий, статистика хранилища, размеры словарей.
- **Логи** — `slog` в формате JSON или text. Per-request сводка `request`
  (система, операция, типы ПД и их количество, число спанов, байты, длительность)
  пишется на уровне `info` и отключается параметром `log.requests` для прогонов
  на максимальный RPS; этапы обработки (`detect`, `filter`, `mask`, `store`)
  логируются на уровне `debug`.

**Почему ПД не попадают в логи и метрики.** Это инвариант, а не договорённость.
В `internal/logging` каждый атрибут проходит через скрабинг-обработчик: ключи из
белого списка проходят как есть, всё остальное санитизируется, а значения,
имеющие форму ПД (длинные строки, группы цифр, ФИО), заменяются на длину и
солевой отпечаток. В `internal/metrics` нет ни одного API, принимающего значение
ПД — записываются только имена категорий и счётчики. В `internal/store` поля
`Original` и `Masked` помечены как защищённые и никогда не логируются.

## Надёжность

- **Под нагрузкой.** `server.max_concurrent` ограничивает число одновременных
  обработчиков `/process`. При насыщении лимитера запрос получает **429** с
  заголовком `Retry-After: 1` (и телом `{"error":"busy","retry_after":1}`).
  Пробы `/health` и `/ready` не отбрасываются лимитером.
- **Таймауты.** `server.process_timeout_ms` ограничивает обработку одного
  запроса через контекст; `read_timeout_ms`, `write_timeout_ms`,
  `idle_timeout_ms` — на уровне `http.Server`. `ReadHeaderTimeout` защищает от
  Slowloris.
- **Деградация.** `server.fail_open` (по умолчанию `true`) — при внутреннем
  сбое `/process` отвечает 200 с неизменённым payload, а не ошибкой: прогон
  останавливается после короткой серии невалидных ответов, поэтому один
  транзиентный сбой не должен ронять весь прогон. Для реального трафика
  оператор должен выключить `fail_open`. Если соответствие для `payload_id`
  пропало (TTL, рестарт, слишком большой payload), обратный шаг возвращает
  присланный payload без изменений и считает `pdguard_demask_fallback_total`.
- **Идемпотентность.** Повторный запрос с тем же `payload_id` безопасен: если
  пришла та же исходная строка, сервис возвращает ту же маску.

## Развёрнутый стенд

Решение развёрнуто и доступно снаружи:

| Адрес | Назначение |
|---|---|
| `https://pereshein.ru/process` | **рекомендуемый эндпоинт** для проверки |
| `https://pereshein.ru/` | демо-консоль: чат с ИИ через pdguard, маскирование и демаскирование |

Порт `8080` на публичном адресе тоже отвечает, но **для проверки его использовать не
стоит**. Измерено: запросы с телом примерно от 900 байт, отправленные на `:8080` из
внешней сети, обрываются на сетевом участке (`RemoteDisconnected`), тогда как ровно те же
запросы на `443` проходят при любом размере — вплоть до 20 КБ. С самого
сервера `:8080` отвечает нормально, то есть дело не в сервисе, а в промежуточном
оборудовании, которое иначе обходится с трафиком на этом порту. Длинные сложные
предложения — самые ценные случаи датасета, терять их на сетевой прослойке нельзя.

Замеры производительности — в презентации и в разделе производительности.

## Тесты и нагрузочный прогон

Go стоит в Docker, поэтому все команды идут через обёртки `scripts/go.sh` и
`scripts/gofmt.sh`.

```bash
# Полный набор тестов
timeout 900 bash scripts/go.sh test ./... -count=1

# Статический анализ
timeout 600 bash scripts/go.sh vet ./...

# Проверка форматирования (пустой вывод = ок)
timeout 300 bash scripts/gofmt.sh -l .

# Нагрузочный прогон (лестница 200/1000/2000 RPS внутри одного контейнера)
bash scripts/bench-local.sh

# End-to-end проверка контракта mask → unmask
bash scripts/smoke.sh
```

Нагрузочный инструмент `cmd/bench` воспроизводит протокол проверяющей системы:
для каждого элемента датасета шлёт прямой запрос под свежим `payload_id`, затем
обратный с той же маской, и считает элемент успешным только если обратный шаг
вернул исходные байты. Ретраи и abort-правило (5 невалидных ответов подряд)
повторяют поведение харнесса.

## Ограничения и план развития

**Ограничения**

- Детекция построена на правилах и словарях, без ML. Редкое имя без словарных
  признаков может пройти незамеченным — справочник дополняется через блок
  `dictionaries`.
- Маска по умолчанию (`stars_keep2`) оставляет по 2 символа с краёв, как в
  примере ТЗ. Есть альтернативы: «всё звёздами» (`stars_all`) и токены (`token`).
- В LLM-цепочке ФИО подставляется в падеже запроса — согласование падежа не
  выполняется.
- Соответствия `payload_id → (оригинал, маска)` хранятся в памяти процесса
  (TTL 30 минут), без шифрования и репликации между узлами.
- LLM-прокси отвечает целиком, без потоковой выдачи.

**План развития**

- NER-модель как второе мнение поверх правил и словарей.
- Общее зашифрованное хранилище соответствий и несколько узлов.
- Потоковый ответ LLM с восстановлением на лету и согласованием падежа.
- Консоль администратора, аудит, интеграция с SIEM, mTLS.
